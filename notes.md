# Заметки по ходу решения

## Что требуется

1. Подсчёт токенов в агенте: для текущего запроса, для всей истории
   диалога, для ответа модели.
2. Сравнить короткий диалог, длинный диалог и диалог, который не влезает
   в контекст модели.
3. Показать рост токенов и стоимости по ходам и то, что ломается при
   переполнении.

## База

Предыдущий проект (AITrenning_Task7) без правок: диалог с историей в JSON,
два типа агентов, веб-интерфейс, цикл хода в `internal/agent/runner.go`.

## Что известно про лимит

- `deepseek-v4-flash` и `deepseek-v4-pro`: контекст **1 048 576 токенов**
  (в документации «1M», точное число выяснилось из отказа API), выход
  до 384K. Источник: <https://api-docs.deepseek.com/quick_start/pricing/>.
- Параметра, ограничивающего вход, в API **нет**. `max_tokens` режет только
  ответ. Переполнение видно только по ошибке в ответ на запрос.
- Официальный токенизатор — Python/HuggingFace
  (`deepseek_v4_tokenizer.zip`), для Go не годится. Документация даёт
  ориентиры: 1 английский символ ≈ 0.3 токена, 1 китайский ≈ 0.6. Про
  русский не сказано — коэффициент подбираем по факту из `usage`.

Отсюда решение: **свой мягкий лимит** `-context-limit` в агенте (для
воспроизводимых опытов на малых числах) плюс **одна настоящая проба** на
истории больше миллиона токенов, чтобы показать, что мягкий лимит
моделирует реальное поведение, а не выдумку.

## План

1. `internal/tokens` — оценка токенов до отправки: веса по классам символов,
   накладные на сообщение и на описание инструмента. Разбивка запроса на
   системный промпт, инструменты, историю и новое сообщение.
2. `Runner`: оценка перед каждым запросом к модели (внутри хода контекст
   растёт с каждым ответом инструмента), сверка оценки с фактом из `usage`,
   события журнала с обоими числами.
3. Мягкий лимит и поведение при переполнении: `fail` (по умолчанию),
   `trim` (выкидывать старые ходы), `off` (пусть отвечает API).
4. Интерфейс: разбивка токенов в панели промпта, факт против оценки под
   ответом, график роста по ходам.
5. Режим отчёта: короткий, длинный и переполненный диалог одной командой,
   таблица роста, сохранение в `examples/`.
6. Настоящая проба переполнения на синтетической истории > 1M токенов.

## Ход работы

### Калибровка оценщика

Первые веса взяты наугад от документации: латиница 0.30 (оттуда),
кириллица 0.50, знаки 0.45, обвязка сообщения 4 токена. Прогон отчёта на
живой модели показал устойчивое завышение:

| сценарий | ходов | средняя ошибка |
|---|---|---|
| короткий диалог | 3 | 32.1 % |
| длинный диалог | 12 | 24.6 % |
| переполнение, fail | 11 | 27.2 % |
| переполнение, trim | 12 | 27.1 % |

Ошибка тем больше, чем короче запрос, — значит, завышены и вес символа, и
обвязка сообщения. Подогнал: кириллица 0.50 → 0.39, знаки 0.45 → 0.36,
цифры 0.50 → 0.40, пробелы 0.10 → 0.08, обвязка 4 → 3. Латиница и
иероглифы остались документальными.

### Лимит для сценария переполнения

С прежними (завышенными) весами длинный диалог упирался в 4000 токенов на
двенадцатом ходе. После калибровки оценка стала честной — и тот же диалог
в 4000 стал влезать целиком (оценка на 12-м ходе ≈3004 против факта 2990).
Сценарий переполнения перестал переполняться. Лимит опыта снижен до 2000:
диалог упирается в него примерно на десятом ходе.

Вывод на будущее: сценарий, который проверяет предел, нельзя привязывать
к числу, полученному из той же сломанной оценки, — иначе он «работает»
ровно до тех пор, пока оценка неверна.

### Проба настоящего переполнения

Первый заход набрал вдвое меньше заказанного: шаг цикла считался как
удвоенный вес длинного сообщения, а пара «короткий вопрос + длинный
ответ» весит примерно вдвое меньше. Вышло ≈528 тыс. токенов вместо
1.05 млн — то есть запрос, который модель приняла бы и выставила бы счёт
примерно на $0.12. Процесс снят до отправки, шаг исправлен на сумму весов
обоих сообщений, добавлена проверка: если набралось меньше лимита модели,
проба не отправляется вовсе.

Настоящий ответ API:

```
This model's maximum context length is 1048576 tokens. However, you requested
1211508 tokens (1211508 in the messages, 0 in the completion).
```

Отсюда два числа. Лимит — ровно 1 Mi, а не круглый миллион из
документации; константа в коде исправлена. И оценщик на этом тексте
занизил на 13 % (1 055 598 против 1 211 508) — на повторяющемся тексте
оценка по классам символов работает хуже, чем на живом диалоге.

### Обрезка ломает кэш

Неожиданное из отчёта: сценарий `trim` потратил на вход на четверть меньше
токенов, чем длинный диалог, но обошёлся в полтора раза дороже. Причина
видна в столбце «из кэша»: пока история дописывается в конец, префикс
запроса не меняется и DeepSeek отдаёт 90+ % входа по цене в тридцать раз
ниже. Первая же обрезка меняет начало истории — кэш обнуляется, и дальше
из него приходит по 256 токенов вместо трёх тысяч.

То есть у обрезки есть цена, которую не видно в счётчике токенов. Если
history-window всё-таки нужен, резать надо редко и помногу, а не по
чуть-чуть на каждом ходе.
