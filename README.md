# Токены и переполнение контекста (DeepSeek, Go + браузер)

Локальное приложение с веб-интерфейсом, в котором агент-справочник по
животным ведёт диалог с памятью между запусками, а рядом с каждым ходом
видно, из чего сложился контекст: сколько токенов занял системный промпт,
сколько описания инструментов, сколько история прошлых ходов и сколько
новый вопрос. После ответа модели оценка сверяется с фактом из `usage`.

Диалог — единственная память агента, и он же — главная статья расхода:
историю модель получает заново на каждом ходе. Поэтому третий вопрос из
трёх слов стоит дороже первого, десятый — дороже третьего, а рано или
поздно история перестаёт влезать в контекст. Это приложение показывает
рост в числах и доводит его до переполнения — сначала своим лимитом, а
потом настоящим лимитом модели.

Развитие предыдущего задания: диалог с историей в JSON, два типа агентов,
инструменты Википедии и GBIF и веб-интерфейс переехали без правок. Новое —
счёт токенов, свой лимит контекста с тремя вариантами поведения при
переполнении, график роста по ходам и два режима без интерфейса: прогон
опыта и проба настоящего переполнения.

## Что нужно

- Go 1.22 или новее;
- ключ DeepSeek API (https://platform.deepseek.com);
- доступ в интернет к `ru.wikipedia.org` и `api.gbif.org`;
- любой современный браузер.

## Запуск

```bash
git clone https://github.com/AlexS8332/AITrenning_Task8.git
cd AITrenning_Task8
cp .env.example .env     # и вписать свой ключ в DEEPSEEK_API_KEY
go run .                 # поднимет сервер и откроет браузер
```


Флаги:

```bash
go run . -context-limit 2000        # свой лимит контекста: переполнение за десяток ходов
go run . -on-overflow trim          # при переполнении выбрасывать старые ходы
go run . -on-overflow off           # не проверять: пусть отвечает API
go run . -context-limit 0           # то же самое, но и оценку не с чем сравнивать
go run . -report examples/report.md # прогнать опыт и записать отчёт, без интерфейса
go run . -probe-overflow            # отправить заведомо слишком длинный запрос
go run . -keep-tools 0              # отправлять модели старые ответы инструментов целиком
go run . -addr 127.0.0.1:0          # свободный порт, программа напечатает какой
go run . -open=false                # не открывать браузер
```

Ключ берётся из переменной окружения `DEEPSEEK_API_KEY` или из файла `.env`
(`.env.local`) в рабочем каталоге или выше по дереву. В git эти файлы не
попадают.

## Три числа про токены

| Что считаем | Где берём | Зачем |
|---|---|---|
| **Текущий запрос** | оценка до отправки, `internal/tokens` | решить, отправлять ли, и показать, из чего он состоит |
| **Вся история диалога** | та же оценка, доля `history` | она и растёт; остальные доли почти постоянны |
| **Ответ модели** | `usage.completion_tokens` из ответа API | точное число, известно только после ответа |

Оценка и факт — разные вещи, и путать их нельзя. Факт приходит в `usage`
ответа и всегда точен. Оценка нужна до отправки: чтобы поймать
переполнение раньше, чем его поймает API, и чтобы показать разбивку — в
`usage` её нет, там одно число на весь запрос.

Точного токенизатора под Go у DeepSeek нет: официальный собран под
Python/HuggingFace. Поэтому оценка идёт по классам символов — латиница,
кириллица, иероглифы, цифры, пробелы, знаки, — плюс обвязка сообщения,
описания инструмента и запроса. Два коэффициента взяты из документации
(английский символ ≈ 0.3 токена, китайский ≈ 0.6), остальные подобраны по
фактическому расходу; как именно — ниже.

Контекст считается не раз в ход, а перед каждым запросом к модели: внутри
одного хода агент может несколько раз позвать инструменты, и каждый их
ответ уходит модели следующим запросом. Пик внутри хода бывает заметно
выше, чем на старте, — интерфейс показывает оба числа.

## Что видно в интерфейсе

- **Промпт хода** — полоска «из чего сложился контекст»: история,
  инструменты, системный промпт, новое сообщение, в токенах и процентах,
  и доля от лимита.
- **Журнал хода** — у каждого запроса к модели оценка (`≈2346 ток. в
  запросе`), у каждого ответа оценка против факта и расхождение
  (`≈2346 / 2472→197 ток. (-5%)`).
- **Итоги хода** — оценка контекста против факта первого запроса, пик
  внутри хода, сколько сообщений выброшено обрезкой.
- **Рост токенов и стоимости** — свёрнутая панель под лентой: столбики —
  токены запроса по ходам (светлая часть — то, что пришло из кэша), линия —
  накопленная стоимость диалога, и та же таблица числами.

## Опыт: короткий, длинный и не влезающий диалог

`go run . -report examples/report.md` прогоняет один и тот же разговор о
рыси в четырёх видах и пишет отчёт: три хода, двенадцать ходов и те же
двенадцать при лимите 2000 токенов в режимах `fail` и `trim`. Полные
таблицы — в [examples/report.md](examples/report.md).

| сценарий | ходов | вход, токенов | выход | стоило | средний ход |
|---|---|---|---|---|---|
| короткий диалог | 3 | 1 174 | 325 | $0.000255 | $0.000085 |
| длинный диалог | 12 | 20 216 | 3 324 | $0.002497 | $0.000208 |
| переполнение, `fail` | 8 из 12 | 7 617 | 1 724 | $0.001314 | $0.000164 |
| переполнение, `trim` | 12 | 14 955 | 2 991 | $0.003574 | $0.000298 |

Что из этого видно.

**Ходов вчетверо больше — токенов в семнадцать раз больше.** Три хода
стоили 1 174 токена на вход, двенадцать — 20 216. Вопросы при этом
короткие: «А от манула?» — четыре слова. Платим не за вопрос, а за
историю, которая уезжает модели заново каждый ход.

**Один и тот же вопрос дорожает.** Первый ход — 281 токен на вход,
двенадцатый — 3 650, ровно в тринадцать раз, и это на разговоре из
двенадцати реплик. Стоимость хода растёт вместе с ним, а не по числу
заданных вопросов.

**Кэш держит цену.** DeepSeek считает совпадающий префикс по цене в
тридцать раз ниже: на двенадцатом ходе из 3 650 токенов входа 3 584
пришли из кэша, и ход стоил $0.000104 — дешевле пятого, где кэша было
768 из 908. Пока история дописывается в конец, префикс не меняется.

**Обрезка ломает кэш, и это видно в деньгах.** Сценарий `trim` прошёл все
двенадцать ходов и потратил на вход на четверть меньше токенов, чем
длинный диалог (14 955 против 20 216), но обошёлся в полтора раза дороже:
$0.003574 против $0.002497. Как только из начала истории выбрасываются
ходы, префикс меняется, и кэш обнуляется: на ходах 9–12 из кэша приходило
по 256 токенов вместо двух-трёх тысяч. Дешёвый на вид приём оказался самым
дорогим сценарием опыта.

## Можно ли установить лимит контекста

Короткий ответ: у модели — нет, у себя — да.

- Контекст `deepseek-v4-flash` и `deepseek-v4-pro` — **1 048 576 токенов**
  (документация округляет до «1M», точное число видно в отказе API), и это
  свойство модели. Параметра, который бы его уменьшил, в API нет:
  `max_tokens` (до 384K) ограничивает только ответ.
- Значит, единственный способ узнать о переполнении со стороны API —
  получить отказ на запрос. Отвергнутый запрос не тарифицируется, но и
  пользы от него нет: ход уже потерян.
- Поэтому лимит живёт в агенте: `-context-limit` и `-on-overflow`. Агент
  считает токены сам и решает до отправки. Заодно это делает опыт
  воспроизводимым: упереться в 2000 токенов можно за десяток ходов, а в
  миллион — за несколько тысяч, и это уже не учебный опыт, а счёт.

Три поведения при переполнении:

| Режим | Что делает | Что теряем |
|---|---|---|
| `fail` | ход не отправляется, ошибка с числами | ход; зато ничего не сломано и ничего не потрачено |
| `trim` | выбрасывает самые старые ходы, пока не влезет | память о начале разговора |
| `off` | отправляет как есть | ничего до ответа API, дальше — сам ход |

Обрезка идёт **ходами целиком**, от сообщения пользователя до следующего:
ответ инструмента без вызова, который его породил, API отвергает. Файл
диалога при этом не меняется — режется только то, что уходит модели, как и
сокращение старых ответов инструментов из прошлого задания.

## Что ломается при переполнении

**Со своим лимитом (`fail`, 2000 токенов).** Диалог оборвался на девятом
ходе, не дойдя до конца:

```
запрос не влезает в контекст: ≈2055 токенов при лимите 2000 (лишних ≈55)
```

Ломается не «что-то в модели», а сам разговор: ход не состоялся, ответа
нет, в историю ничего не добавилось. Следующий вопрос упрётся в то же
самое — диалог мёртв, пока историю не сократить. Зато ничего не потрачено
и ничего не испорчено: отказ случился до запроса.

**С обрезкой (`trim`).** Диалог дошёл до двенадцатого хода, но платой
стала память. К последнему ходу выброшено четырнадцать сообщений — всё
начало разговора. На вопрос «Напомни, как меня зовут и с чего мы начали»
агент отвечать уже не по чему: имя было в первом сообщении, которого в
контексте больше нет. Агент не ошибается и не врёт — он честно не помнит,
и внешне это выглядит как амнезия посреди разговора.

**С настоящим лимитом модели.** `go run . -probe-overflow` набирает
историю на ≈1 055 000 токенов и отправляет как есть
([examples/probe.log](examples/probe.log)):

```
Проба переполнения: 252 сообщений, оценка ≈1055598 токенов (лимит модели 1048576).
Ответ API через 8.6 с:

шаг 1: API вернул 400 Bad Request: This model's maximum context length is 1048576 tokens.
However, you requested 1211508 tokens (1211508 in the messages, 0 in the completion).
Please reduce the length of the messages or completion.
```

Три вещи из этого ответа:

1. Настоящий лимит — **1 048 576** токенов, то есть 1 Mi, а не круглый
   миллион из документации. Число стоит знать точно: разница в 48 тысяч
   токенов — это десяток длинных статей.
2. API отвечает отказом на весь запрос, а не обрезает историю сам.
   Восемь с половиной секунд ушло на отправку четырёх мегабайт, и ход
   потерян целиком. Отвергнутый запрос не тарифицируется, но время и ход
   уже не вернуть — ради этого свой лимит и нужен.
3. В отказе есть точное число токенов запроса, и это единственный
   бесплатный способ проверить оценщик на больших числах: он насчитал
   1 055 598 против 1 211 508, то есть занизил на 13 %. На повторяющемся
   тексте оценка по классам символов врёт сильнее, чем на живом диалоге,
   и это её честная граница.

## Насколько точна оценка

Оценка по классам символов — прикидка, и её честность надо мерить, а не
объявлять. Мерилка встроена в отчёт: у каждого хода рядом стоят оценка и
факт из `usage`.

Первые веса были взяты от документации плюс догадка (кириллица 0.50
токена на символ, знаки 0.45, обвязка сообщения 4 токена). Прогон на живой
модели показал устойчивое завышение — и тем большее, чем короче запрос:

| сценарий | средняя ошибка до подгонки | после |
|---|---|---|
| короткий диалог | 32.1 % | 3.5 % |
| длинный диалог | 24.6 % | 3.7 % |
| переполнение, `fail` | 27.2 % | 3.0 % |
| переполнение, `trim` | 27.1 % | 1.9 % |

Подгонка: кириллица 0.50 → 0.39, знаки 0.45 → 0.36, цифры 0.50 → 0.40,
пробелы 0.10 → 0.08, обвязка сообщения 4 → 3. Латиница (0.30) и иероглифы
(0.60) остались документальными. После этого на живом русском диалоге
оценка держится в пределах ±6 % на отдельных ходах и 2–4 % в среднем.

Двух оговорок это не отменяет. Оценка систематически завышает на коротких
запросах (обвязка весит заметно на трёхстах токенах) и занижает на
длинных — вплоть до −13 % на миллионе токенов повторяющегося текста, что
видно по пробе. Поэтому решение «отправлять или нет» стоит принимать с
запасом от лимита, а не впритык, а факт всегда брать из `usage`.

## Как хранится история

Один диалог — один файл `history/<id>.json`: метаданные, `messages` для
модели и `turns` для интерфейса. У каждого хода теперь есть `context` —
оценка с разбивкой, пик внутри хода, факт первого запроса, лимит и число
выброшенных сообщений. Запись атомарная, битый файл при старте
пропускается с предупреждением.

## Как устроено

```
main.go                   запуск: флаги, ключ, инструменты, история, сервер
report.go                 опыт без интерфейса: сценарии, отчёт, проба переполнения
internal/tokens           оценка токенов по классам символов, разбивка запроса
internal/llm              клиент DeepSeek: сообщения, tools, tool_calls, usage, прайс
internal/tools            Tool, реестр, HTTP с кэшем; инструменты Википедии и GBIF
internal/agent            контракты и Runner: цикл хода, счёт токенов, лимит контекста
internal/agents           агенты: с инструментами и чат; каталог типов
internal/history          Conversation, Turn; JSON-хранилище; сокращение старых ответов
internal/runs             менеджер диалогов: ходы, подписчики SSE, запись после хода
internal/server           HTTP API: /api/agents, /api/conversations, /api/turns
web/                      страница, стили, скрипт без сборки; markdown-рендер вшит
```

## API

```
GET    /api/agents                       типы агентов, каталог истории, время старта сервера
GET    /api/conversations                список диалогов
POST   /api/conversations                новый диалог с первым сообщением
GET    /api/conversations/{id}           диалог целиком: сообщения, ходы, счётчики контекста
DELETE /api/conversations/{id}           удалить диалог и файл (409, пока идёт ход)
POST   /api/conversations/{id}/turns     следующий ход
GET    /api/conversations/{id}/file      файл диалога как он лежит на диске
GET    /api/turns/{id}                   состояние хода и его журнал
GET    /api/turns/{id}/events            поток событий хода (SSE)
```
